# Validation report — pystatistics `ordinal_multinomial` v5.0.0

> This report validates **pystatistics ordinal_multinomial v5.0.0**, installed from **pypi**. Evidence lives in `artifacts/ordinal_multinomial/v5.0.0/`. It was generated by `render_report.py` from frozen artifacts — **do not edit numbers by hand**; fix the artifact or the renderer and re-render.

**Subsystem:** Ordinal & multinomial logistic regression — polr + multinom (`pystatistics.ordinal (polr) + pystatistics.multinomial (multinom)`)

## 1. What statistical procedure is implemented?

First-time whole-surface validation of two grouped models. ORDINAL: polr fits the proportional-odds / cumulative-link model P(Y<=j|x) = g^{-1}(alpha_j - x'beta) by L-BFGS-B on the analytic gradient plus a safeguarded-Newton polish, matching MASS::polr for the logit (renamed from 'logistic' in 5.0), probit and cloglog links, and additionally supporting the cauchit and loglog links added in 5.0 (loglog matched to MASS::polr; cauchit validated against an independent MLE because MASS::polr's cauchit under-converges); the ordered thresholds alpha are the category intercepts (X carries no intercept column), and the observed-information standard errors are the finite-difference Hessian of the analytic gradient mapped to natural threshold coordinates by the delta method. MULTINOMIAL: multinom fits the baseline-category softmax MLE by L-BFGS-B, matching nnet::multinom with weight decay=0; the LAST class (highest code) is the reference (nnet baselines on the FIRST level, so the R factor is releveled so the two baselines coincide), the caller supplies the intercept column, and standard errors come from the closed-form softmax Hessian X'WX. Every quantity is validated against R on identical float64 inputs (each design dumped to CSV and read by both engines). The contract is TWO-TIER: coefficients / thresholds / log-likelihood at an optimizer tolerance (the two libraries use different optimizers), fitted probabilities tight. Both models expose a GPU backend (backend='gpu' float32, 'gpu_fp64' CUDA-only, 'auto'); the fp32 GPU path was the CF-1 exposure (a normal-equations Gram inverted in single precision) that this pass caught silently-wrong and fixed at 4.6.9. Both models also expose predict(X, kind='class'/'probs') (added 4.6.10, matching R's predict.polr / predict.multinom; the argument was named 'type' before 5.0), validated on held-out data. In 5.0 the polr link value 'logistic' was renamed to 'logit' and predict's 'type' argument to 'kind'; the estimators are otherwise unchanged and reproduce the blessed 4.6.10 numbers.

## 2. Which algorithms are used?

- polr — proportional-odds / cumulative-link model (optimizer tier vs MASS::polr). L-BFGS-B on the analytic gradient in an unconstrained log-gap threshold parameterization, then a safeguarded-Newton polish whose acceptance is a half-Newton-decrement score test (not the optimizer's success flag). Links: logit (proportional odds; 'logistic' was renamed to 'logit' in 5.0), probit, cloglog, and — added in 5.0 — cauchit and loglog. logit/probit/cloglog/loglog are matched to MASS::polr's method; cauchit is validated against an independent scipy MLE because MASS::polr's cauchit under-converges on the heavy-tailed Cauchy likelihood. The observed information is the forward-difference of the analytic gradient (what MASS::polr does with Hess=TRUE); its inverse is mapped from raw log-gap to natural threshold coordinates by the delta method, so the reported threshold and slope standard errors are on the same scale as MASS::polr. Data separation is detected as a non-positive-definite observed information and rejected with ConvergenceError (fail-loud).
- multinom — baseline-category multinomial logit / softmax MLE (optimizer tier vs nnet::multinom). L-BFGS-B on the softmax cross-entropy with analytic gradient; the last class (highest code) is the identifiability reference (beta_ref = 0). The unpenalized fit (the default) matches nnet::multinom(decay=0) once the R response factor is releveled so nnet's first-level baseline coincides with the last-code reference. The caller supplies the intercept column (matching nnet's formula intercept). Standard errors come from the closed-form block Hessian H[j,k] = X' diag(W_jk) X with W_jj = p_j(1-p_j), W_jk = -p_j p_k — assembled once and inverted. Fitted class probabilities and the predicted class are reported directly.
- GPU path (both, backend='gpu'/'gpu_fp64'/'auto'). The float32 GPU path keeps X and y on device and runs the same L-BFGS-B on a torch likelihood (autograd gradient for polr, log_softmax for multinom) — the large-n WIN. As of 4.6.9 the post-fit variance-covariance is computed in FLOAT64: polr forms the observed-information Hessian on the GPU in fp64 on CUDA (host finite-difference on MPS, which has no fp64), multinom forms its closed-form softmax Hessian on the host in fp64; the small (K-1+p) or (K-1)p Hessian is then inverted once, in fp64, on the host with a positive-definiteness gate. This removes the CF-1 fp32-Gram silent-wrong (see the audit section) while leaving the fast fp32 fit untouched.
- Two-engine convention matching. The validation matches the ESTIMATOR and CONVENTION between engines, never a different one: the polr LINK equals the MASS::polr method; multinom's decay=0 equals nnet's unpenalized MLE; the multinom baseline is releveled so the reference class coincides; the design matrix (treatment-contrast dummies for factors, intercept handling per model) is built once and handed to both engines via the dumped CSV, so agreement is to fp64 round-off of identical numbers, not contaminated by a design mismatch.

## 3. How does it compare to R MASS::polr / nnet::multinom?

polr is validated against MASS::polr (method='logistic'/'probit'/'cloglog', Hess=TRUE) — coefficients, ordered thresholds (zeta), their standard errors from the observed information, log-likelihood, AIC/deviance, the fitted class probabilities, and predict() on held-out data vs predict.polr. multinom is validated against nnet::multinom(decay=0), with the R response factor releveled so nnet's first-level baseline coincides with pystatistics' last-code reference — the (K-1)x(1+p) coefficient matrix, its standard errors, the log-likelihood/AIC/deviance, the fitted probabilities (reordered to code order), and predict() on held-out data vs predict.multinom. Datasets: MASS::housing (ordinal, expanded to individual rows), a well-conditioned proportional-odds and softmax synthetic (the clean coefficient-tier anchors), iris (3-class) and MASS::fgl (6-class) as real-data quasi-separation cases, plus constructed complete/quasi separation, rare/collapsed category, and unbalanced designs. The cauchit link (added in 5.0) is validated against an independent scipy cauchit MLE rather than MASS::polr, whose cauchit under-converges.

Also compared against: independent scipy cauchit ordinal MLE (reference for polr link='cauchit', because MASS::polr's cauchit under-converges).

## 4. What numerical tolerances are expected?

- **g1_polr_two_tier:** polr vs MASS::polr, two-tier with the link matched between engines. TIER A (optimizer): coefficients and ordered thresholds agree to max|Δ| ~2e-7 (logistic/probit) to ~1.4e-5 (cloglog) on housing, ~3e-7 on the synthetic continuous+factor design, ~1.4e-4 on the rare-interior-category design; standard errors to a relative ~2e-7..5e-5; log-likelihood |Δ| ~1e-9..1e-6 (housing logistic identical to R to 8 significant figures, -1739.5746). TIER B (tight): the implied fitted class probabilities (computed from the library's own coef+thresholds) reproduce R's predict(type='probs') to max|Δ| ~1e-7..5e-5. R15: the bare default polr(y,X) uses the logit link (renamed from 'logistic' in 5.0) and reproduces the explicit-logit fit exactly.
- **g1_new_links:** The two polr links added after 4.6.10 — cauchit and loglog — validated as supported (5.0). loglog vs MASS::polr(method='loglog') agrees to optimizer tier (coef/zeta max|Δ| ~4e-6, loglik |Δ| ~5e-9 on housing and the synthetic). cauchit is validated NOT against MASS::polr but against an INDEPENDENT scipy cauchit MLE (neutral-start multi-restart Nelder-Mead + BFGS polish on the standard Cauchy-CDF cumulative-link likelihood): pystatistics matches that independent MLE to coef/threshold max|Δ| ~6e-6 (housing) / ~2e-8 (synthetic) and loglik |Δ| ~7e-9 / 0. MASS::polr's cauchit is NOT a reliable reference — its optim under-converges on the heavy-tailed Cauchy likelihood, reporting a strictly worse optimum (loglik -1752.77 vs the true -1742.16 on housing, a 10.6 gap; -1472.45 vs -1465.82 on the synthetic, a 6.6 gap); pystatistics reaches the true MLE.
- **g1_multinom_two_tier:** multinom vs nnet::multinom(decay=0), baseline releveled. Where the MLE is IDENTIFIED (well-conditioned designs): coefficients agree to max|Δ| ~4e-5 (3-class) .. 3.5e-4 (5-class), standard errors to a relative ~2e-5..6e-5, log-likelihood |Δ| ~1e-8..1e-6, fitted probabilities to ~3e-6..2e-4 — an optimizer-tier agreement (nnet uses BFGS, pystatistics L-BFGS-B). R15: the bare default (decay=0) matches. Quasi-separation (iris setosa-separable, fgl small classes): the coefficients are NON-IDENTIFIED (the MLE is at infinity) so the engines agree on log-likelihood (|Δ| ~1e-5 iris, ~1e-2 fgl) and FITTED PROBABILITIES (~5e-5 iris, ~2e-3 fgl), not on the runaway coefficients — matching nnet's own behaviour.
- **g1_hard_cases:** R10 — matching R's failures, not only its numbers. polr complete separation: pystatistics rejects the non-PD observed information with ConvergenceError; MASS::polr also refuses (glm.fit emits the 'fitted probabilities numerically 0 or 1' separation warnings and polr then errors) — both engines refuse a separated fit. multinom complete separation (4.6.9): raises NotPositiveDefiniteError (the observed information is not positive definite; the covariance is not identified) — fail-loud, matching polr; nnet instead returns the degenerate fit with a non-convergence flag. Rare interior category and a continuous+factor contrast design agree at the optimizer tier above.
- **g2_fidelity_fail_loud:** 12/12 fail-loud checks pass, no silent substitution (RIGOR A6 / Guarantee 2). polr and multinom both RAISE (never quietly substitute) on: an unknown polr link name (ValidationError 'Unknown link', NOT a silent logistic/logit fallback — the valid set is logit/probit/cloglog/cauchit/loglog); l2>0 requested on the GPU backend; an unknown backend; backend='gpu_fp64' without CUDA (RuntimeError: MPS has no fp64); y with a missing/gapped level, y not starting at 0, non-integer y; non-finite X. NOTE: at 4.6.10 cauchit/loglog were unimplemented and this suite asserted they fail loud; 5.0 implements them (validated in g1_new_links), so the fail-loud contract is now exercised by a genuinely unknown link name.
- **g3_performance_cpu:** CPU vs R across problem size (Guarantee 3, same estimator): pystatistics is at or FASTER than R at every size, with no complexity-class gap. polr py/R ratio 0.55..0.88 across n=500..20000 (py log-log slope 0.88 vs R 1.01); multinom 0.32..0.68 across n (slope 0.80 vs R 1.00) and 0.18..0.38 across K=3..12 categories (slope 1.09 vs R 1.58 — pystatistics scales BETTER with the number of categories than nnet). pystatistics also computes the full observed-information Hessian for standard errors, which nnet/optim also do (Hess=TRUE / summary), so this is like-for-like.
- **g1_predict:** predict() vs R (added 4.6.10, TIER B tight). On a train/test split both models predict on held-out data for type='probs' and type='class'. polr.predict vs predict.polr (all 3 links): predicted probabilities agree to max|Δ| ~1e-5, predicted classes match EXACTLY (200/200). multinom.predict vs predict.multinom (3-class and 5-class): probabilities ~3e-5, classes exact (400/400). In-sample predict(X_train) reproduces the stored fitted_probs (polr now exposes fitted_probs/predicted_class for parity with multinom). predict fails loud on an invalid type or a column-count mismatch.
- **gpu_g3_corollary:** The GPU corollary to Guarantee 3 (CUDA, RTX 5070 Ti): the float32 GPU path beats the CPU in its intended large-n regime — polr ~50x and multinom ~120x over the CPU at n=100000 (design-dependent; both are large, and the GPU wall time stays roughly flat while the CPU grows linearly). Small n is slower (fixed dispatch overhead, expected). The 4.6.9 CF-1 fix moved only the post-fit vcov to fp64, leaving the fp32 fit — and therefore the speedup — unchanged. The gpu_fp64-vs-CPU pivot (R11) is machine-precision, isolating the fp32 residual from the hardware.

## Constitutional compliance & GPU backend reconciliation

Constitutional-compliance audit (R4) of both public surfaces. Selector taxonomy: polr uses link= (Amendment A3 method->link; the internal resolver and one legacy info-dict key still carry 'method', but the user-facing argument and the .link accessor are 'link', and as of 4.6.9 the unsupported-link error reads 'Unknown link'); multinom takes no link (single logit). Both use the backend= device+precision encoding ('cpu'/'gpu'/'gpu_fp64'/'auto', no use_fp64). Both …Solution objects report .z_values (not .t_values) — correct per Amendment A3 for these asymptotic-normal (Wald) models — with .standard_errors, .p_values, .conf_int, .vcov, .summary(); OrdinalSolution adds threshold_* accessors, and MultinomialSolution gained a .warnings accessor at 4.6.9 for parity with OrdinalSolution. core.exceptions types are used (ValidationError, ConvergenceError, NotPositiveDefiniteError, RuntimeError for the fp64-needs-CUDA guard).

**GPU backend reconciliation.** Both GPU float32 paths formed the model information matrix (X'WX-structured Hessian) and inverted it in the working (float32) precision. This is the CF-1 exposure named in CARRY_FORWARD.md — a normal-equations Gram inverted in fp32 — which materialised SILENTLY-WRONG on CUDA: at cond(X)~1e4 (a near-collinear design the CPU/fp64 path fits correctly, and where gpu_fp64 correctly fails to converge) backend='gpu' returned converged=True with a 100%-wrong, NEGATIVE-variance standard error for polr, and ~40% wrong (white-box 160% + negative variance) for multinom. Caught mid-run and treated as an R16 showstopper. Fixed at 4.6.9 by computing the variance-covariance in float64 (Hessian assembled on-device in fp64 on CUDA where it is fast, on the host on MPS which has no fp64; inversion + PD gate once in fp64), verified on CUDA to have NO negative variances and fp32-tier SE error (<2e-2) across a cond(X) sweep from 1e1 to 1e4 — while keeping the ~50x/~120x large-n GPU speedup. Unlike gam (whose GPU path never won and was removed), this GPU path wins decisively and was fixed, not removed.

**Findings:**

- **F-0 — fp32 GPU Hessian inversion returned silently-wrong / negative-variance standard errors** _(fixed in 4.6.9 (R16))_: backend='gpu' inverted the X'WX Hessian in float32; on ill-conditioned designs (cond(X)>=~1e3) it silently returned wrong and even negative variances with converged=True, CUDA-proven. Fixed by computing the vcov in float64 (on-device on CUDA, host on MPS) with a positive-definiteness gate; the fast fp32 fit is unchanged so the GPU still wins ~50x/~120x at n=100k. See the cf1 and gpu_perf studies.
- **F-A — multinom reported converged=True with a meaningless covariance on complete separation** _(fixed in 4.6.9)_: On complete/quasi separation the observed information is not positive definite; multinom used to return a pseudo-inverse (negative variances) with converged=True. It now raises NotPositiveDefiniteError — matching polr, which already rejects a non-PD observed information — rather than returning a covariance a user would trust. Quasi-separated-but-identified designs (iris, fgl) still return, with the honest large standard errors.
- **F-B — polr reported an unsupported link as 'Unknown method'** _(fixed in 4.6.9)_: polr(link='cauchit') failed loud (good — no silent substitution) but the message said 'Unknown method', mismatching the link= argument (an Amendment-A3 vestige). It now reads 'Unknown link' with no silent fallback. (At 4.6.10 loglog/cauchit were unsupported and named in this message; 5.0 implements both links — now validated in the g1_new_links study — so only a genuinely unknown name triggers this error.)
- **F-C — polr had no predict / fitted-probability accessor** _(fixed in 4.6.10)_: Originally OrdinalSolution had no predict()/fitted-probability property and MultinomialSolution had fitted_probs/predicted_class but no predict(newdata) — a gap versus R, which ships predict.polr and predict.multinom. Both models now expose predict(X, type='class'/'probs') and polr gains fitted_probs/predicted_class (parity with multinom). Validated on held-out data vs R: probabilities ~1e-5, classes exact (see the predict study).

## 6. What are the known limitations?

- polr supports the logit (renamed from 'logistic' in 5.0), probit, cloglog, cauchit and loglog links — 5.0 added cauchit and loglog, which 4.6.10 left unimplemented. logit/probit/cloglog/loglog are validated against MASS::polr; cauchit is validated against an independent MLE because MASS::polr's cauchit under-converges and is not a trustworthy reference for that link. A genuinely unknown link name still fails loud ('Unknown link', no silent substitution).
- Prediction: both models expose predict(X, type='class'/'probs') (added 4.6.10), matching R's predict.polr / predict.multinom, plus in-sample fitted_probs/predicted_class. predict takes the design matrix directly (no formula interface): X must be laid out as at fit time — no intercept column for polr (the thresholds are the intercepts), including the intercept column for multinom.
- multinom coefficients are non-identified under (quasi-)separation — where a class is perfectly predicted the MLE is at infinity. multinom agrees with nnet on the log-likelihood and fitted probabilities there but the coefficients diverge in both engines; on COMPLETE separation (a non-positive-definite information matrix) multinom now fails loud (NotPositiveDefiniteError) rather than returning a meaningless covariance. This is stricter than nnet, which returns the degenerate fit with a non-convergence flag.
- The GPU float32 path is for large n: it beats the CPU decisively past n~1e4 (polr ~50x, multinom ~120x at n=100k) but is slower for small n (fixed device-dispatch overhead) — the CPU is the right choice there. On MPS the vcov Hessian is computed on the host in float64 (Metal has no fp64); on CUDA it is computed on-device in fp64 for polr and on the host for multinom (measured faster than a second device upload). Standard errors are identical across backends by construction (all float64).
- The optimizer tier is a real (small) gap: MASS::polr uses optim, nnet::multinom uses BFGS, pystatistics uses L-BFGS-B, so coefficients agree to an optimizer tolerance (~1e-4..1e-7 on well-identified designs) rather than to machine precision. Log-likelihood and fitted probabilities are the tight quantities. This is a documented contract, not a defect.
