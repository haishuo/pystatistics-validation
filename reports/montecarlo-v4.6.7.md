# Validation report — pystatistics `montecarlo` v4.6.7

> This report validates **pystatistics montecarlo v4.6.7**, installed from **pypi**. Evidence lives in `artifacts/montecarlo/v4.6.7/`. It was generated by `render_report.py` from frozen artifacts — **do not edit numbers by hand**; fix the artifact or the renderer and re-render.

**Subsystem:** Monte Carlo — bootstrap resampling & permutation testing (montecarlo) (`pystatistics.montecarlo`)

## 1. What statistical procedure is implemented?

The montecarlo module provides nonparametric resampling inference matching R's boot package: boot() (ordinary/balanced/parametric bootstrap with index/frequency/weight statistic conventions, optional strata, injectable seed), boot_ci() (all five R boot.ci interval types — normal, basic, percentile, studentized/bootstrap-t, and BCa), and permutation_test() (two-group permutation of a test statistic with the Phipson-Smyth (count+1)/(R+1) p-value). This is a first-time validation across the WHOLE public surface, combining the first-time correctness pass and the red-team. Because bootstrap/permutation results depend on the random resamples and R's RNG differs from numpy's, naive bit-matching against R is invalid; the module is validated with a three-part contract for STOCHASTIC methods: (1) DETERMINISM (R6) — a supplied seed (numpy.random.default_rng) makes every result bit-reproducible on re-run (CPU and GPU), and the deterministic observed statistic t0 always matches; (2) the TIGHT tier — a genuine R boot::boot is run, its resample index matrix exported, and the IDENTICAL indices fed to pystatistics, so the statistic and CI arithmetic (which is deterministic given the replicates) is compared to machine precision or the defined convention, isolating cross-language RNG divergence; (3) the STATISTICAL-EQUIVALENCE tier — each engine runs its own large-B resampling and the replicate summaries, CIs, and permutation p-values agree within Monte-Carlo error ~1/sqrt(B), plus a coverage study on a seeded DGP with a KNOWN true mean. The module is CPU-first fp64; it also carries a GPU path (Apple MPS float32, CUDA float64) that vectorizes the sample mean (boot) and difference-in-means (permutation) across B resamples — the corpus's cleanest embarrassingly-parallel GPU workload. Bootstrap/permutation resampling and statistic evaluation form no normal-equations Gram, so the CF-1 fp32-Gram trailing-eigenvalue exposure does not apply.

## 2. Which algorithms are used?

- Bootstrap resampling (boot). Ordinary nonparametric bootstrap draws n indices with replacement per replicate (numpy Generator.choice); balanced bootstrap pre-generates a pool in which each observation appears exactly R times, shuffles, and splits into R samples; parametric bootstrap generates each replicate from a user ran_gen(data, mle, rng). The user statistic follows R's stype convention — 'index' (indices into data), 'frequency' (bincount weights), or 'weight' (normalized weights) — with optional within-strata resampling. Returns t0 (statistic on the original data, deterministic), the R×k replicate matrix t, bias = mean(t)-t0, and se = sd(t) (ddof=1). Matches boot::boot's t0/t/bias/se on shared resample indices to machine precision.
- Confidence intervals (boot_ci), all five boot.ci types. normal: the bias-corrected normal interval 2*t0-mean(t) ± z*sd(t) (identical to R). basic (pivotal): 2*t0 - quantile(t, {1-a/2, a/2}). perc: quantile(t, {a/2, 1-a/2}). studentized (bootstrap-t): pivots z*=(t*-t0)/se* from per-replicate variance estimates, CI = t0 - sd̂*quantile(z*, {1-a/2, a/2}). BCa (bias-corrected and accelerated): z0 = Phi^{-1}(proportion of t* < t0) (deterministic given the replicates), acceleration a from Efron's delete-1 JACKKNIFE influence a = ΣL³/(6(ΣL²)^1.5), then adjusted percentile levels α = Phi(z0 + (z0+z_α)/(1-a(z0+z_α))). Quantiles use numpy's default (type-7) interpolation; R's boot.ci uses its own norm.inter (interpolation of order statistics on the normal scale) — a documented convention difference, see tolerances.
- Permutation test (permutation_test). Concatenates the two groups, permutes the combined vector R times (numpy Generator.permutation), and recomputes the user statistic(x, y) on each split. The p-value uses the Phipson-Smyth correction (count+1)/(R+1) with count over |perm|>=|obs| (two-sided), perm>=obs (greater), or perm<=obs (less). For small n the exact permutation distribution is the enumeration of all C(n, n1) group assignments; pystatistics' large-B Monte-Carlo p-value matches that exact p-value within Monte-Carlo error.
- Determinism & RNG (R6). All randomness flows through an injectable seed: numpy.random.default_rng(seed) on CPU, torch.manual_seed(seed) on the GPU (same device). Same seed => bit-identical replicates and CIs on re-run; the default seed=None is intentionally non-reproducible (the injectable seed is the determinism handle) while the observed statistic t0 is always deterministic. The GPU permutation kernel builds permutations by random-key argsort (torch.rand + argsort), which produces unbiased permutations (the null permutation distribution is centered at 0).
- GPU path (Guarantee-3 corollary; the 4.6.7 opt-in). The GPU vectorizes exactly two closed-form statistics — the sample mean (boot) and the difference in means (permutation) — generating all B resamples on device and reducing them in parallel. The statistic form is NEVER inferred: the caller declares it via gpu_statistic ('mean'/'mean_diff'). The dispatcher routes to the GPU only for a declared, vectorizable design; an explicit backend='gpu' that cannot be honored (missing declaration; balanced/parametric/strata/2-D; a declared statistic whose observed value != the mean) RAISES rather than silently substituting a backend or a statistic. backend='auto' with no GPU-supported declaration runs on CPU, disclosed via solution.backend_name. The reduction is float32 on MPS (no gpu_fp64 for montecarlo — the honest subset {cpu, gpu, auto}) and float64 on CUDA.

## 4. What numerical tolerances are expected?

- **g1_determinism_r6:** Same seed => bit-identical results on re-run: boot t/t0/bias/se and all boot_ci intervals identical; permutation_test perm_stats and p-value identical; GPU (MPS) boot/permutation identical on re-run. The default seed=None is non-reproducible by design (documented — pass a seed), while t0 is always deterministic. 6/6 CPU + GPU reproducibility checks pass.
- **g1_tight_machine_precision:** On R's genuine SHARED resample indices, the deterministic quantities match to machine precision: the replicate statistic t and t0 to ~1e-15 (law corr max|t_py - t_R| = 1.1e-15; city ratio 5.1e-15), bias/se derived from t to machine precision, the NORMAL CI to ~1e-15 (identical formula), and the BCa bias-correction z0 to ~1e-17 (identical definition). This isolates the statistic + CI arithmetic from cross-language RNG divergence and is the tier where real bugs hide.
- **g1_tight_conventions:** Two CI conventions are documented, not defects. (1) QUANTILE INTERPOLATION: basic/perc/studentized use numpy's type-7 quantile; R boot.ci uses norm.inter (order statistics interpolated on the normal scale). On shared replicates they agree to ~1e-3 (law/city perc 3e-4..8e-4 at R=5000) and shrink with R; the studentized formula reproduces the textbook type-7 result exactly and agrees with R to the same quantile convention (3.6e-3), amplified only where the bootstrap-t pivot is heavy-tailed. (2) BCa ACCELERATION: pystatistics uses Efron's JACKKNIFE acceleration a; R boot.ci's default empinf uses the REGRESSION influence estimate. z0 is identical; the a values differ slightly (law: jackknife -0.076 vs regression -0.083), which shifts the BCa endpoints in the tails by a documented convention amount (law bca abs 7.7e-3, city ratio 5.5e-2 at R=5000). Both are textbook-standard BCa; calibration is settled by the coverage study, not by matching R's a.
- **g1_equivalence_mc:** Independent-RNG, large-B (B=60000): the bootstrap se agrees within Monte-Carlo error (law 1.2%, city 0.2% relative) and the normal/basic/percentile CI endpoints agree to <2% of interval width; BCa's endpoint gap is the documented acceleration convention (reported, not gated). Permutation p-values (B=200000) match the base-R EXACT enumeration to <1e-2 and an independent R Monte-Carlo run to <1e-2 for all three alternatives (two-sided/greater/less on the sleep data).
- **g1_coverage_study:** Nominal-95% CI coverage over 1000 seeded samples from a KNOWN-truth lognormal DGP (n=40, skewed — the hard regime): normal 0.921, basic 0.914, percentile 0.929, BCa 0.930 (binomial SE ~0.7%). All simple methods under-cover at this small-n skew as expected; BCa covers best, demonstrating that its bias/acceleration correction is doing real work. This is the ultimate CI correctness check and is reported honestly, including the small-n-skew under-coverage that motivates BCa.
- **g2_fidelity_fail_loud:** No silent substitution (Guarantee 2 / A6). The 4.6.7 GPU opt-in is fail-loud: backend='gpu' without gpu_statistic raises; a non-vectorizable config (balanced/parametric/strata/2-D) raises; a declared gpu_statistic='mean' over a non-mean statistic raises (verified on MPS and CUDA); the CPU default is unaffected. The default invocation (R15) works: bare boot() (R=999, cpu) and permutation_test() (R=9999, two-sided, cpu) return finite results. gpu_statistic is validated at the boundary (only 'mean'/'mean_diff'/None accepted).
- **g3_performance_cpu:** Same O(B) complexity class as R (empirical slope ~1.0), so no R1 complexity gap. For an arbitrary Python statistic on tiny data both engines loop per replicate; pystatistics carries a constant-factor lag at tiny n (law corr 0.40x, city ratio 0.29x, sleep perm 0.56x of R's speed at n=10-15) that is fixed Python per-replicate overhead. An n-sweep shows the lag reverses as the per-replicate statistic cost grows: parity at n~1000 and 3.4x FASTER than R at n=10000 (numpy vectorization beats R's per-replicate cor). The lag is a bounded, self-reversing tiny-n cost (R2), not a defect; the large vectorized win is GPU-only.
- **g3_gpu_corollary:** The GPU path (the declared-gpu_statistic mean / mean-difference) meets the Guarantee-3 GPU corollary on both devices. SPEED: Apple MPS 25-43x (boot mean) / 6-15x (perm) over the CPU across the range; CUDA (RTX 5070 Ti, sm_120, torch 2.11+cu128) 59-158x (boot) / 28-116x (perm) — R11 same-precision (CUDA-fp64 vs CPU-fp64) so this is pure hardware win. ACCURACY: on shared resample indices the MPS float32 mean drifts only ~1.3e-7 from the fp64 reference even at n=100000 (well within the 1e-5 fp32 tier — torch's reduction is numerically stable, so there is NO fp32-accumulation silent-wrong), and the CUDA fp64 path is exact (~5e-16). RNG: reproducible with a seed, and the argsort-key permutation is unbiased (null distribution centered at 0). montecarlo exposes no gpu_fp64 selector (honest subset).

## 6. What are the known limitations?

- The BCa acceleration parameter uses Efron's delete-1 JACKKNIFE influence values; R's boot.ci uses the REGRESSION influence estimate (empinf default type='reg') by default. Both are standard BCa; z0 is identical; the acceleration differs slightly and shifts the BCa endpoints in the tails by a documented amount (e.g. the city ratio lower endpoint differs ~5% of interval width). A user comparing BCa endpoints to boot.ci should expect this convention difference; the coverage study confirms pystatistics' BCa is well-calibrated (best of the four methods on the hard skewed DGP).
- basic, percentile, and studentized intervals use numpy's type-7 quantile interpolation, whereas R's boot.ci uses its norm.inter (order statistics on the normal scale). The difference is ~1e-3 on shared replicates and shrinks with the number of replicates; it is only material in an extreme tail (e.g. a heavy-tailed studentized pivot at small n). Both are valid quantile estimators.
- permutation_test's two-sided p-value counts |perm| >= |obs|, which assumes the test statistic is null-centered at zero. For a difference statistic (mean(x)-mean(y), the intended use and the docstring example) this is correct and matches exact enumeration; for a statistic NOT centered at zero under the null (e.g. a ratio of means, centered ~1) the |.| convention diverges from the proper two-sided (2*min-tail): on a small example the ratio gave 0.89 where the enumerated 2*min-tail two-sided is 0.40. Pass a null-centered (difference) statistic, or use alternative='greater'/'less'. Documented footgun, not a silent-wrong for the intended use.
- The GPU path vectorizes ONLY the sample mean (boot) and the difference in means (permutation); any other statistic runs on the CPU. With backend='gpu' the statistic form must be declared via gpu_statistic ('mean'/'mean_diff') and is verified against the observed value on the data — an arbitrary Python statistic cannot execute on the GPU and raises rather than falling back silently. This explicit opt-in replaced (in 4.6.7) a one-sample auto-detection that could silently compute the mean for a different statistic; see the provenance note.
- The bootstrap coverage of any CI method is a small-sample property: on a strongly skewed DGP at n=40 all methods (including BCa) under-cover the nominal 95% somewhat (0.91-0.93 measured). This is an inherent property of bootstrap intervals at small n with skew, not a defect in the implementation; BCa reduces but does not eliminate it. Reported honestly by the coverage study.
- montecarlo exposes no gpu_fp64 backend (the honest subset is {cpu, gpu, auto}) because replicate counts, not precision, dominate resampling; the GPU reduction is float32 on Apple MPS and float64 on CUDA internally. The MPS float32 mean was verified to stay within the fp32 tier (~1e-7) even at n=100000, so there is no silent fp32-accumulation error; a user needing double precision should use backend='cpu' or a CUDA device.

## 7. Which version of pystatistics do these results apply to?

- **Library version:** 4.6.7  ·  **Install source:** pypi
- **Frozen:** 2026-07-05  ·  **Reference:** R boot::boot / boot.ci + exact enumeration
- **Hosts / devices:** **arm+r** — CPU (numpy 2.4.6) + R boot 1.3.32 / stats 4.5.2; **mac-mps** — Apple mps (torch 2.12.1); **forge-cuda** — NVIDIA GeForce RTX 5070 Ti (torch 2.11.0.dev20251226+cu128, CUDA 12.8)
- **Provenance:** First-time validation of pystatistics.montecarlo (bootstrap + permutation resampling) across its whole public surface — boot, boot_ci (all 5 CI types), permutation_test — combining the first-time validation and the red-team in one pass. Stochastic methods are validated with a three-part contract: (R6) seed determinism; a TIGHT tier that shares R's genuine boot resample indices with pystatistics so the statistic + CI arithmetic is compared to machine precision, isolating cross-language RNG divergence; and a statistical-equivalence tier (independent RNGs, large B) plus a known-DGP coverage study. The pass drove one R16 emergency stop: the GPU backends inferred whether the user's statistic was the mean / mean-difference from a SINGLE resample and could then silently compute the mean for a different statistic on backend='gpu' — a silently-wrong result. Fixed in 4.6.7: the one-sample inference was removed and replaced with an explicit gpu_statistic opt-in ('mean'/'mean_diff') that is fail-loud (missing declaration, non-vectorizable config, or a declared statistic that does not match the data all raise; auto falls back to CPU disclosed). Identical float64 inputs feed both engines (law, city, sleep from the central HDF5 store; the R reference reads the same values and, in the tight tier, the same resample indices).
